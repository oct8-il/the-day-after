The annotation

Some fields on an incident record are authored prose rather than plain strings. They carry a small, closed annotation: seven features, one citation syntax, one coverage rule. This file is what the author writes to, what the validator rejects against, and what the interpreter renders.

v1.1 · 22 September 2026 · DIA-365 · headings added by DIA-419

1 · What this governs

Three things read the annotated fields, and they have to agree about what the marks mean:

  • The author, writing an incident's overviews during its per-item pass (DIA-306).
  • The validator, which refuses to publish a record that breaks these rules (DIA-371).
  • The interpreter, which turns the marks into a screen on both the mobile and the desktop item page (DIA-372).

A contract with three consumers does not belong inside any one of them, so it lives here. Where an issue and this file disagree, this file is right and the issue is stale.

This supersedes §10 of docs/mobile-item.html on every point below. §10 was written when the plan was plain markdown with cite chips as ordinary links; both of those are now wrong.

What this is not: general markdown. The set is closed, and it is closed deliberately — every feature added here is a feature two renderers, a validator and a Hebrew RTL layout have to agree on forever.

2 · The annotation set

Exactly seven features are supported.

FeatureSyntaxWhat it is for
Bold**text**The bottom line. In an overview it carries the opening sentence's verdict; mid-sentence it marks the finding itself.
Highlight==text==Emphasis of a different kind: the words inside a sentence a reader should not skim past — a figure, a date, a phrase lifted from an official text.
Bullet list- itemParallel findings that are not ordered.
Numbered list1. itemA sequence: steps of a plan, stages of a process.
Hyperlink[text](https://…)Navigation. A report, a law, a background page. Takes the reader somewhere else.
Source chip[[text]](i13-c08)Citation. Points into this incident's own claims. §3.
Section heading## textStructure. Breaks a long overview into sections a reader can scan. Asserts nothing, so it cites nothing. §3.

The heading is the one feature that lives outside a cite

Everything else in the set is written inside a span, because everything else is part of a statement. A heading is not a statement — it names the section under it — so it stands in the gap between spans, on a line of its own:

[[הלֵיד, שאומר מה נכשל.]](i13-c01)

## איפה השרשרת נשברת

* [[**אין מי שמכריע:** …]](i13-c02)
* [[**עיכוב מובנה:** …]](i13-c05)

One level. # through ###### all mean the same heading, because the reading system has exactly one heading style and refusing five of them would be pedantry about a difference no screen can show. ## is what to write.

A heading may carry the set's inline marks — bold, highlight, a hyperlink — and it may not carry a chip. ## [[text]](c01) is an error rather than a heading: a heading asserts nothing, so there is nothing in it for a source to hold up. Inside a span a hash is not a heading at all; the mark is dropped and the words stay, like any other unsupported syntax (§5).

Added 22 September. Overviews are written as a lead, headings and lists (DIA-415) — a shape ruled in after the reading system was settled, and one the contract had no way to write. The renderer used to strip # everywhere and the coverage rule counted a heading line as an unsourced statement, so the feature could not have been used by accident before it existed. DIA-419.

Bold and highlight are not interchangeable

Bold is structural — it is how an overview states its conclusion first. Highlight is local — it picks out the load-bearing words inside a sentence that is already being read. A highlight stretched over a whole sentence is a misuse; so is bolding a date.

Markdown has no standard for highlight. The de-facto convention ==text== is adopted because it collides with nothing else in the set, and because it is what every editor that supports highlighting at all already uses.

Chips and hyperlinks ship side by side

This reverses an earlier reading in which a chip stood in place of a link. They are different things and a sentence may carry both.

Only a chip discharges the sourcing rule. A hyperlink never does. A sentence resting on a bare URL is not sourced, however authoritative the page behind it — the ledger's guarantee is that every published assertion points at a claim record with a quote read off its page, and a link is not one.

Everything else is dropped

Images, blockquotes, tables, nested lists, and anything else that looks like markdown are stripped silently by the renderer — not rendered as literal characters, and never shown to a reader as an error. §5 says why the silence is on the renderer's side only.

3 · Source chips and the coverage rule

A chip is a hyperlink's shape with doubled brackets, and a claim id where the URL would be:

[text](https://…)            hyperlink
[[text]](i13-c08)            source chip
[[text]](i13-c08, i13-c11)   source chip, several claims

One rule to learn, and the two kinds of link stay apart both on the page and in the source file.

Explicit scope

Each chip states exactly which text it covers. The span is written, not inferred.

Implicit scope was considered and rejected: the obvious alternative — a chip at the end of a sentence covering backwards to the previous chip — makes the boundary something nobody has to write down, and therefore something nobody has to think about. A citation boundary that is never stated is an opening for negligence.

Cites are a pre-pass, above markdown

The cite spans are extracted first; markdown is then parsed inside each span, never across one. So a span may hold paragraph breaks, bullets, numbered lists, bold, highlight and hyperlinks, and one chip may wrap a single sentence, several, or an entire overview.

A markdown construct that opens inside one span and closes in another is an error, not a rendering puzzle.

The coverage rule

The coverage rule: outside a cite span, only whitespace, list markers and section headings may appear. Anything else is uncovered text, and the record fails to validate.

That is the whole of it. It is stated as a property of the text rather than of the sentence, so that it holds no matter how the author breaks up the prose.

On the page

The chip draws at the end of its span, carrying the source-type mark and a +N when the cite holds several claims. Tapping it opens the cited claims — quote, source, date, link — and highlights the span it covers. Because the span is authored, that highlight is exact rather than guessed.

In RTL the chip sits inside the Hebrew run; latin claim ids stay isolated so the punctuation does not reorder around them.

Lists, and the one place a marker may sit outside a span

The coverage rule lets a list marker stand in a gap, and that is not an oversight — it is how a list whose items each rest on a different source is written. Both forms are legal, and a renderer has to draw both:

[[* the first item
* the second item]](i13-c08)        one source behind both items

* [[the first item]](i13-c08)        a source per item - the marker
* [[the second item]](i13-c11)       stands in the gap before its span

In the second form the marker opens a list item and the span that follows is its content. The marker is never part of the cited text: a citation covers a claim, not the glyph in front of it. Consecutive items are one list, not a run of one-item lists, and each item carries its own chip.

Both forms draw, since 20 September. renderAnnotation used to map spans and drop gaps, so a marker written the second way disappeared and the item rendered as a paragraph — with no error, because the validator was right to accept it. It now reads the gap before each span: a lone marker there sets that span's marker, and the renderer gathers consecutive items of the same kind into one list. Nothing in either pool used list syntax, so no screen changed. DIA-382.

4 · Where it applies

Annotation is not a property of the record; it is a property of named fields. Everything else is a plain string and is rendered as one.

FieldAnnotationCoverage rule
summaryyesenforced
summaries[].textyesenforced
poll.failureyesenforced
poll.statusyesenforced
poll.questionyesnot enforced
poll.caveatyesnot enforced
he——
card_line——
photo.*, feedback_strip——
Parent.description——

Every annotated field gets the same errors — nested, unclosed or empty cite; a markdown construct crossing a span; an id that does not resolve to a claim of this incident; a duplicate id within one cite. Coverage is the only rule that varies.

The exemptions are deliberate, and they are all one reason: text that asserts nothing has nothing to rest on. The caveat states an absence, and an absence has nothing to cite. The question is put to the reader rather than asserted, so enforcing coverage there would force a chip onto text that is not a claim. A section heading names what follows rather than saying anything about it, which is the same rule applied to a line instead of a field — so a heading is exempt wherever it is written, including in the fields marked enforced. Both still parse as annotation — bold, highlight, lists, hyperlinks and chips are all available in them — and a chip written in either is checked like any other.

5 · The two readers

The renderer and the validator treat a mistake differently, on purpose.

The validatorThe renderer
AudienceThe author, before the record shipsA reader, after it ships
On unsupported syntax—Drops it silently
On a broken ruleFails the buildRenders what it can

A reader must never be shown a syntax error; that is the renderer's silence. An author must never be allowed to ship one; that is the validator's job. The two are not a contradiction — they are the same decision seen from either end of the pipeline.

What the validator names

  1. Uncovered text — anything but whitespace, a list marker or a section heading outside a cite span, in the fields §4 marks enforced.
  2. A heading with no words — usually a cite written into the heading line, which is named as its own error because the fix is different.
  3. A nested cite, an unclosed cite, an empty cite.
  4. A markdown construct crossing a span boundary.
  5. An id that does not resolve to a claim of this incident.
  6. A duplicate id within one cite.

Accepted without complaint: inline bold and highlight mid-sentence, bullets, numbered lists and hyperlinks inside a span; a span running over paragraph breaks; a reached stage with no overview at all, which falls back to rendering that stage's claims.

6 · The sources carousel

Nothing about the carousel is authored. It is derived from the chips in the text: one card per cited document, deduplicated by url — falling back to source + date where a url is absent — and ordered by first appearance in the text. Publication, source type, date, link.

So a single source backing four sentences appears once, and two separate pieces from the same publication stay two cards. It is a list of documents, not of claims.

7 · Worked example

[[**מערכת ההתרעה ביישובי העוטף מעולם לא נבנתה לזהות חדירה קרקעית.** היא תוכננה
להתרעת רקטות, ובתרחיש של פריצת גדר לא היה לה מה להשמיע.]](i13-c03, i13-c04)

[[ועדת הבדיקה קבעה שהפער היה מוכר, ו[הדוח המלא](https://example.com/report)
פורסם רק ב==2025==.]](i13-c11)

Reading it: two cite spans, so two chips, each drawn at the end of its own span. The first covers a bolded bottom line and the sentence that explains it, and rests on two claims. The second carries a hyperlink to the report — navigation, sourcing nothing — and a highlight on the year, and rests on one claim. Between and around the spans there is only whitespace, so the text is fully covered and the record validates.
