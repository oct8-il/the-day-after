None of it blocks the build: the claims fallback covers missing overviews, and every authored field degrades to something honest. It does block the page looking finished, which is worth stating plainly before slide-by-slide review starts — the first phone you pick up will show fallbacks.

Renumbering invalidates published work. Claude outputs/five-posts.html hard-codes the number from the file id — i13→13, i29→29, i01→1 — and the IG dry run went out that way. Numbering by published position makes i13 כשל מס׳ 12 on the site. The generator needs the same computed number, and anything already posted is stale. Regenerating the five posts is a task in this plan; anything already public is a call only you can make.
The rating strip breaks the static guarantee. "The site is built from the repository, there is no database and no API" is currently a fact about the project. A star rating that goes somewhere needs an endpoint — a form service, a serverless function, or a third-party form. Decide which before Phase 8; until then the strip is built and inert.

3 · Data and schema

Schema changes

// data/schema/index.ts

- Summary = { stage, lines: [{ text, cites: string[] }] }
+ Summary = { stage, text: string }        // markdown; cites are [label](i13-c08) links

  Incident = {
    id, parent, he,
-   summary: string,                        // narrative, item-specific
+   summary: string,                        // markdown, SYSTEMIC — no 7.10 manifestation
+   card_line?: string,                     // short statement for slide 6 cards
+   opinion?: { failed, since, caveat },    // slide 5's three head lines
+   photo?: {                              // two crops, independent of each other
+     portrait?:  { file, photographer, source, licence, place, year },   // the gate
+     landscape?: { file, photographer, source, licence, place, year },   // slide 6 card
+   },
    illustrative, claims, summaries?
  }

Validator

  • Parse the markdown rather than the array: every sentence carries at least one link, every link resolves to a claim of this incident.
  • Accept inline bold mid-sentence (the emphasis rule from slide 2 supersedes the old bold-opening-line ruling).
  • Reject a summary that names a date in October 2023 — a cheap proxy for the systemic rule, worth trying and easy to drop if it fights the writing.
  • Photo fields validate together: a file with no licence fails rather than rendering an uncredited photograph. Dimensions are not checked — the crop is trusted.
  • The two crops are independent: an item may have a portrait and no landscape, or the reverse. Each falls back on its own — the gate to the number ghost, the card to its bare tint.

4 · Jump mode (new, unspecced)

Decided in the interview, absent from v2.0 of the spec, and the only hidden gesture on the page. Written here so it can be reviewed before it is built.

  • Arming: press and hold ~400ms on the stage rail (slides 3 and 4) or on the dot row (any slide). The finger stays down for the whole interaction.
  • Moving: slide along the strip. The page scrubs live — each stage or slide renders as it is passed.
  • State: the strip goes to full strength, the page behind drops to ~40%. Both transitions are ~120ms so arming reads as a change, not a glitch.
  • Landing: release. Mode ends with the finger; there is nothing to dismiss.
  • Reach: the rail moves within its own stack only — an unreached rung stays inert on slide 3. The dot row crosses all six slides, slide 4 included.

Jump mode is an accelerator, never the only route. Every stage and slide it can reach is also reachable by ordinary sequential navigation, which is what makes it safe to leave undiscovered — and what makes the page usable with a screen reader, where the gesture does not exist. See §7.

Implementation notes, from the platform rather than the design. A long press on iOS raises the selection callout and the magnifier unless the strip carries -webkit-touch-callout:none, user-select:none and touch-action:none. Arming must cancel the deck's own scroll-snap so the two gestures do not fight. There is no haptics API in Safari, so the feedback is visual or it does not exist. Reduced-motion should drop the scrub to a direct jump on release, keeping the dim.

6 · Verification

Three layers, because pixels alone cannot see a rule and rules alone cannot see a screen.

  1. Frozen 390×844 baselines — every slide, every stage page, i13 and i20, photo and no-photo.
  2. Behavioural assertions, which survive a legitimate redesign: the locator renders at right:14px as measured, not as authored; a rung's y-position is identical on slides 3 and 4; an item at the last stage produces five dots; the stage chip on a card keeps contrast over its photo; the page itself never scrolls.
  3. Gesture tests — Playwright touch emulation for swipe, long-press arming, scrub and release, and the push-once history rule.
The RTL trap, as a test rather than a memory. padding-inline-end and align-items:flex-end resolve to the left in this page, which cost two review rounds. Every edge-anchored element gets an assertion on its measured getBoundingClientRect(), so it can never quietly flip again.

7 · The six open questions, answered

Breakpoint decided

The mobile deck renders at (max-width: 599px) and (min-height: 600px). Everything else — tablets, landscape phones, desktops — gets the existing item page.

  • 599px wide covers every phone in portrait, from a 280px folded cover screen to a 430px Pro Max, and stops below the 600–768px band where tablets begin. A 390-wide design stretched to 760 is the thing the whole reimagining exists to avoid.
  • 600px tall is the guard the spec never had. The deck is a fixed-height frame — six slides, a footer on a rule, 26px of home-indicator padding, a vertical rhythm drawn at 844. A landscape phone is 390px tall; the frame cannot survive it, and the desktop page handles that shape today.
  • Height is 100dvh, not 100vh — iOS Safari's collapsing URL bar makes vh taller than the visible viewport, which would push the footer under the chrome exactly where the next-slide label lives.
  • Between 320 and 599px the frame is fluid, not scaled: the 390 baseline sets the proportions, side gutters stay 20px, and type does not shrink. A scaled 390 canvas would blur text on a 430 screen.

Where the ratings go decided

Supabase, called from the client. A single table, insert-only:

feedback( id, item_id, rating int 1..5, created_at, device_key )
  RLS: anon may INSERT, may not SELECT.
  • It keeps output: 'export' intact — no serverless function, no build-target change, no runtime to operate. The static site stays static; one fetch goes out to a third party.
  • It is the same instance the full slide 5 will need for public answers and the ballot, so this is not a throwaway: the star strip is the first small use of the store the post-MVP page depends on.
  • device_key is a random id in localStorage — enough to stop the same phone rating twenty times, not an identity. The UI shows the saved state from that key.
  • The anon key is public by nature, so the table is spammable. Acceptable here: it is developer feedback, nothing renders from it, and no one sees it but you. Before the ballot ships it needs a real gate (Turnstile or a rate limit), and the standing rule already caps the damage — public answers never move a stage.

Say the word if you would rather not add the dependency; the alternative is a hosted form service, which is less work now and useless for the ballot later.

Share decided

Web Share API where it exists — on iOS and Android that is the native sheet, which is the whole point on a page reached from Instagram. Where it does not, the fallback copies the item link, not the deep link: /item/i13/ with no hash, so a shared link always opens at the gate. A short toast confirms the copy.

Keyboard and screen reader decided

The question was whether the deck has any route through it that is not a gesture — on a phone, that means VoiceOver and TalkBack, where swipe means "next element", not "next slide". The answer is that nothing is gesture-only:

  • The deck is a scroll container of six <section>s, each labelled in Hebrew (השער, סקירת הכשל, …). A screen reader moves through them in DOM order; scroll-snap follows focus, so the visible slide and the spoken one stay together.
  • Slides 3 and 4 are the same shape one level down — a labelled section per stage page.
  • The footer's previous/next labels are real links to the slide hashes, so they work as ordinary navigation for anyone who never swipes.
  • A hardware keyboard gets arrow keys: left/right across slides, up/down within a stack. Cheap to add, and it is how the Playwright gesture tests will drive the deck.
  • Jump mode has no keyboard or AT equivalent, and needs none — it reaches nothing that sequential navigation does not.
  • prefers-reduced-motion drops the live scrub to a direct jump on release, and the deck's slide transitions to instant. The dim stays: it is state, not motion.

Stale social posts closed

Nothing is live; the five posts get regenerated from the new numbering. The generator reads the same computed number as the site, so the two cannot drift again.

Desktop page on a phone closed

Not a goal. No link, no escape hatch, no "view desktop version". A phone under the breakpoint gets the deck.

The last two

Card photo credit deferred by Roy to Phase 8

The gate has a credit slot; the 111px card has none and cannot grow, and most of these images are CC BY-SA, which requires attribution. Not decided now — Roy asked to be reminded when Phase 8 begins, and the Phase 8 gate carries that reminder. The three candidate answers, so the reminder arrives with its options: one credits line at the foot of slide 6; a credits page linked from אודות; or landscape crops only from sources that need no attribution.

Does the star strip show on every item decided

A global default with a per-item override. site.feedbackStrip is the switch; an incident may carry feedback_strip: false (or true) to differ. One field, and the strip can be taken down everywhere by editing one line when enough answers have arrived.

Why the default should stay uniform. The strip asks about the site, not the failure, so the item is not really the axis the decision lives on — and it costs a card, so per-item switching means a reader swiping through several failures sees slide 6 hold four cards, then three, then four, with no reason they can perceive. The override exists for the case where one item genuinely should not carry it; turning it into the normal mechanism is what makes the slide look unstable.
