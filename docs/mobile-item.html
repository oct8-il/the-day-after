The mobile item page

The item page on a phone is a slideshow post of six slides. This is what each slide holds, what the chrome does, how it behaves under a finger, and which rules the data has to satisfy for any of it to render.

1 · Stance and shape

Most phone visitors arrive from a social post about one failure, so the item page is the front door and has to carry its own context. It keeps the control panel's stance — a finite, enumerated set of tracked problems, each with a computed state — without looking like a shrunken control room.

It is a slideshow post, not a story. That distinction decides the chrome: nothing runs on a timer, nothing counts down, the reader sets the pace, and slide 1 is a cover rather than the first frame of something in flight.

This document defines the data shape — not the other way around. Every screen here is drawn for the ideal case, and §10 is what those screens demand of the data, not a reading of what the data happens to be today. Where implementation cannot meet a demand, that is a compromise: it belongs in §12 as a known shortfall, and the design stays where it is. A screen is never narrowed to fit a field that already exists.

2 · Foundations

Frame and direction

  • Design frame 390 × 844, dir="rtl", lang="he".
  • Side gutter 20px. On slide 3 the body's end gutter is 36px to clear the locator.
  • Bottom padding 26px under the footer row for the home indicator. No fake status bar, ever.

Where the deck takes over

  • @media (max-width: 599px) and (min-height: 600px). Below that, the deck; anywhere else — tablet, landscape phone, desktop — the existing item page.
  • 599 wide covers every phone in portrait, from a 280px folded cover screen to a 430px Pro Max, and stops below the band where tablets start. A 390-wide design stretched to 760 is the thing this reimagining exists to avoid.
  • 600 tall is the guard. The deck is a fixed-height frame with a vertical rhythm drawn at 844; a landscape phone is 390px tall and cannot hold it. The desktop page already handles that shape.
  • Height is 100dvh, never 100vh — iOS Safari's collapsing URL bar makes vh taller than the visible viewport, which would push the footer under the browser chrome exactly where the next-slide label lives.
  • Between 320 and 599 the frame is fluid, not scaled: 390 sets the proportions, gutters stay 20px, type does not shrink. A scaled 390 canvas blurs text on a 430 screen.
  • Both trees ship in the same HTML at the same URL and the media query picks one. No route split, no user-agent sniffing, no JavaScript swap — the site is a static export and there is no server to ask.

Deep links and history

  • Hash, not path: /item/i13/#3 for a slide, /item/i13/#3-s2 for a stage page inside one. No extra static pages, and the position survives a refresh.
  • The first move pushes one history entry; every move after it replaces. Back returns to the gate from anywhere in the deck, a second Back leaves the page. This matters because most readers arrive inside Instagram's in-app browser, where Back is the only way out.
  • A shared link is always the bare item URL — never the reader's current hash. See §9.
RTL trap. In this page padding-inline-end and align-items:flex-end resolve to the left. Anything that must sit against the right edge is positioned physically (right: 14px). This cost two review rounds; measure a render rather than trusting the eye.

3 · Chrome

Breadcrumb

One path, top right: 7 באוקטובר › העורף האזרחי › כשל מס׳ 13. Leaf in full ink at 600; ancestors at 60–68% opacity; chevrons at 45%. Never split across two corners.

Slideshow dots

Six dots, 6px, gap 7px, centred above the footer. Active dot full ink, the rest at 30%. First slide is the rightmost dot. No numeric counter anywhere — the dots are the counter.

Jump mode

The locator's rungs are 5px wide, far under any touch-target minimum, so they are not tappable. Both strips instead accept a long press: the stage rail on slides 3 and 4, and the dot row on every slide.

  • Arming — press and hold ~400ms on the strip. The finger stays down for the whole interaction.
  • Moving — slide along it. The page scrubs live: each stage or slide renders as it is passed.
  • State — the strip goes to full strength and the page behind drops to ~40%, both over ~120ms, so arming reads as a change rather than a glitch.
  • Landing — release. The mode ends with the finger; there is nothing to dismiss and nothing can be left switched on.
  • Reach — the rail moves within its own stack only, so an unreached rung stays inert on slide 3. The dot row crosses all six slides, slide 4 included.

Jump mode is an accelerator, never the only route. Everything it reaches is also reachable by swiping and by the footer's slide links, which is what makes it safe to leave undiscovered — and what keeps the page usable with a screen reader, where the gesture does not exist.

Platform notes. A long press on iOS raises the selection callout and the magnifier unless the strip carries -webkit-touch-callout:none, user-select:none and touch-action:none. Arming must cancel the deck's own scroll-snap or the two gestures fight. There is no haptics API in Safari, so the feedback is visual or it does not exist. Under prefers-reduced-motion the scrub becomes a direct jump on release — the dim stays, because it is state rather than motion.

4 · Slide 1 — the gate השער

The gate is the post's slide 1 recomposed for 390 × 844 — not the 4:5 post image letterboxed. Top to bottom: breadcrumb, stage rail, then the title block anchored to the bottom, dots, footer.

Photo treatment

Full-bleed to all four edges, duotoned in the current stage's colour, lighter than the post. The image is greyscale; the tint is a colour-blend layer over it, so any photo works and legibility never depends on the original's colours.

Stage rail (gate only)

Vertical, right edge, attached to the breadcrumb rather than the title. Rungs 4 × 30px, chronological downward, each standing free — no track runs behind them; a continuous line reads as one object and the stages are not one object — the same direction slide 3 scrolls. Labels sit to their left in full wording; the current stage is bold in its own colour; an unreached rung is dashed and preceded by a deliberate gap. The age line 18 ימים אחרי 7.10 · 25.10.2023 sits directly under the current stage's label.

Title block

  • Title: Frank Ruhl Libre 31px/1.18, white, text-wrap:balance, bottom-anchored.
  • Source line: תחקיר צה״ל · כאן חדשות · ועוד 2 מקורות — document, outlet, then the count of the others. No מקור: prefix, no date (the age line already carries time).
  • Credit, bottom left: צילום: <name> · <source> · <licence>.

Computed, not authored

  • The source line — the highest-authority official or oversight claim names the document, the earliest press claim names the outlet, and the remainder are counted: ועוד N מקורות. An item with no official source names two outlets instead. Nothing here is written by hand.
  • The breadcrumb leaf and the item number — כשל מס׳ N is the incident's position in published.json, not its file id, so the number and מתוך 29 can never disagree. The share-post generator reads the same number.
  • The photo — the gate uses the incident's portrait crop. Slide 6's card uses a separate landscape crop. Two independent fields: either may be absent, and each falls back on its own.

No-photo fallback

The identical screen minus the image: a stage-colour field falling to black — what the duotone leaves when there is no photo — a hairline texture so the surface isn't dead, and the item number as a near-transparent 196px serif ghost with מתוך 29 beside it. The credit slot is simply empty. Nothing on the screen announces that a photo is missing.

5 · Slide 2 — סקירת הכשל

The failure at the systemic level. Rule of thumb: had the attack been on 8 October instead of 7, this text would not change; only the manifestation would.

  • The slide title סקירת הכשל sits in a fully-rounded chip — radius 999px, so the corner radius is always half the height — on a rgba(233,230,223,.10) ground with a hairline border, 11.5px/700, letter-spacing .08em. This chip is unique to slide 2; every other slide wears its title bare.
  • Lead sentence at 18px, then paragraphs at 15px, then dashed lines for what the system could not do.
  • No stage rail, no photo, no item title on this slide.
  • Sources carousel anchored to the bottom of the content column: cards 212px, outlet · two-line clamped quote · date. The card is the link — no קישור label.
Where this text comes from. incident.summary itself, rewritten to be systemic and written in markdown — not a new field beside it. The desktop page and the link preview inherit the same sentences, which is the point: the systemic description is the better description everywhere, not only here.

Emphasis

Bold is spread through the text the way an AI overview does it — the key phrase in each passage — not a fully bold opening line. This supersedes the earlier DIA-365 ruling that the opening sentence is simply bold.

Source chips

Each sentence ends with a chip: a coloured dot for the source type plus the type name, and +N when a sentence rests on more than one. Pill shape, 11px/600, rgba(233,230,223,.10) ground. A chip is a markdown link whose target is a claim id.

6 · Slide 3 — מה נעשה מאז

A vertical stack, chronological downward, opening on the current stage — but only the stages the item actually reached. The ones it has not are slide 4. Claims live under the stage they belong to; there is no flat list of all claims any more.

Why split the stack. An item early in its life had a stack that was mostly empty pages: כשל מס׳ 20 sits at stage 1, so four of its five pages said nothing had happened. Split, the shape of an item is legible from the dots alone — how much is behind it, how much is not. The two slides are the same component with a different filter.

Page head

The slide title מה נעשה מאז comes first, bare and right-aligned like every other slide’s — slide 3 was the one screen missing it. Everything below is pushed down to make room. Then one group, in this order, closed by a hairline rule before the body:

  1. Status tag as the page title — square corners (radius 3), stage-colour fill, dark ink #1b1d16, 19px/700, e.g. 4 · יושם. An unreached stage gets the same tag as a dashed outline in muted ink.
  2. The stage definition, 13.5px at 74% ink.
  3. Date, then age: 25.10.2023 · 18 ימים אחרי 7.10.

On the current stage only, a gold pill sits to the left of the status tag, bottom-aligned with it and deliberately much smaller — 10px/700, dark ink on #e0a44a, fully rounded: סטטוס נוכחי — the words alone, no day count. It is the same gold that rings the current rung in the locator, so the two say the same thing in the same colour.

A definition may not use its own term. מה יושם is not a definition of יושם. The three written so far:
1 · זוהה — מה שקרה בשטח, כפי שנרשם בתיעוד ציבורי
4 · יושם — התיקון דווח כמבוצע בשטח בידי הגוף האחראי
5 · אומת עצמאית — גוף שאינו הגוף האחראי בדק את התיקון בשטח ופרסם ממצאים
The date and the age are computed from the earliest claim asserting that stage — nothing in the data says when a stage was reached. Stage 1 therefore carries the date its manifestation was documented (19.10.2023 for כשל מס׳ 13), not 7.10 itself. That settles D3.

Page body

Identical in kind to slide 2 — lead, paragraphs, dashed lines, scattered bold, a chip per sentence, sources carousel at the bottom. Stage 1 additionally hosts the evidence map, and the map comes before the carousel.

A reached stage with no written overview falls back to its claims — quote, source and date rendered directly under the head group, carousel unchanged. An overview improves the page; it does not gate it, and every published item renders from the first build.

7 · Slide 4 — מה עוד לא נעשה

The same component as slide 3 with the opposite filter: the stages the item has not reached, opening at the next one. Everything structural is inherited — head group, locator geometry, footer, the nested vertical scroll — so this section only records what differs.

What differs from slide 3

  • No gold pill. סטטוס נוכחי marks the current stage, and the current stage is never on this slide.
  • No gold ring in the locator, for the same reason. Only the viewed-stage ring appears.
  • No sources carousel. There is nothing to cite for something that has not happened.
  • The back pill walks back a slide — right-pointing chevron, landing on slide 3's current stage.
  • The centre footer arrows appear only when this stack holds more than one page. כשל מס׳ 13 has one stage left, so its slide 4 shows no arrows; כשל מס׳ 20 has four, so it does.

Which stage it opens on

The next one — the lowest-numbered stage not yet reached. For an item at stage 4 of 5 that is stage 5; for an item stuck at stage 1 it is stage 2, and stage 1's slot at the top of the locator stands empty.

A regressed item keeps its current stage on slide 3. When an item's current stage has moved backwards, that stage has still been reached, so it belongs to מה נעשה מאז along with the gold סטטוס נוכחי pill. Slide 4 never holds the current stage, whatever route the item took to get there.
An item at the last stage has no slide 4 — the slide is skipped entirely, and that item is a five-slide post with five dots. There is no "nothing left" screen; a slide with nothing to say is not shown.

The page itself

No colour, no carousel, and the body is composed differently from a reached stage: the head group stays where it is, and everything under the rule is centred horizontally and vertically as one column.

  1. The computed statement, 17px bold — לא תועד אימות בלתי תלוי של היישום.
  2. One line naming who would count as a checking body — on stage 5 only, where "who checks" is the whole content of the stage. Stages 2–4 go straight from the statement to the mark, and the screens below show both shapes.
  3. An hourglass mark: a 28px outline glyph in warning yellow #d9a54f on a 58px round backdrop at rgba(217,165,79,.14).
  4. Directly beneath it the days-since numeral at 38px/700, and beneath that — not beside it — ימים מאז שהיישום דווח at 13px.
  5. The dashed יודעים אחרת? box with הגישו מקור, centred, part of the same group.

Absence is the content; nothing on the page apologises for it. The hourglass is the only place in the item page where a warning colour appears.

8 · Slide 5 — דעת הציבור

The slide where the reader is addressed. It exists in two forms: an MVP that shows the question and says answering opens later, and the full version that carries both opinion registers and a ballot. The full version is the only screen in the item page that scrolls vertically — about 1,960px, a little over two screens.

Head (both versions)

  • Slide title דעת הציבור, right-aligned; everything under it centred, in Assistant. No status chip, no grouping box, no rule — slide 3's head does not apply here.
  • Three summary lines, centred: what failed, what has been reported since, and a dimmer third line for caveats. The first two carry source chips; the caveat carries none, because an absence has nothing to cite.
  • The question, 22px/700. It is generic in substance, phrased in the item's context: האם התרעות החדירה שהותקנו נותנות מענה לכשל המקורי? — never an item-specific curiosity.
  • No stage age anywhere on this slide. Content starts 46–52px below the breadcrumb, not at the top edge.
Only the MVP ships. The registers and the ballot are designed and specified below, and none of it is built in this pass — the question, the dimmed scale and הגישו מקור are the whole screen at launch. The whole MVP head is authored per incident: the question (opinion.question) and the three summary lines (opinion.failed, .since, .caveat). The question stays generic in substance and phrased in this item’s context, as the head rule above requires — a stage-generic string reused verbatim across items is a cheaper thing than the screen asks for. Keeping it fresh when an item moves is an editorial job, not a reason to weaken the question.

MVP

The 1–5 scale is shown dimmed inside a dashed box headed המענה ייפתח בהמשך, so the reader sees what is coming without it pretending to work, plus the one live action: הגישו מקור.

The two opinion registers (full version)

Both come from the desktop and keep their distinction — published analysis is named and institutional, public answers are many anonymous voices.

Ballot and its states

  1. The question repeats directly above the ballot under the label מה דעתכם?.
  2. Empty: five 56px circles, anchored בכלל לא … במידה מלאה (1 on the right), and בחרו דירוג אחד.
  3. Selected: the chosen number fills gold with a soft ring, דירגתם 2 — אפשר לשנות, an optional comment box, and a gold שמרו את התשובה.
  4. Saved: התשובה שלכם נשמרה with a check, a quiet outline-only שינוי התשובה, and the comment rendered as the reader's own bubble in the public register — the rating picks the lane and colour (1–2 clay left, 3 mixed centre, 4–5 sage right).
  5. Then the distribution: the desktop's review shape — a large mean beside rows from 5 down to 1 with percentages.
The rule that governs this whole slide: public answers never move the stage. Only a documented outside check does; the answers tell us where to look. It is printed on the screen, under the distribution.

9 · Slide 6 — הלאה

The last slide, and the only place share lives. It closes the post rather than continuing it: a sign-off line, four other tracked failures, the way out to all 29, and the share action. No creed, no address.

Head

  • Sign-off תודה על הקריאה. in the slide-title slot — same 11.5px/700, .08em, 55% ink, right-aligned, as סקירת הכשל and דעת הציבור.
  • Section row beneath it: עוד כשלים במעקב at 16px/700 on the right, the count 4 מתוך 29 at 12px muted on the left.

Actions

  1. כל 29 הכשלים — quiet outline, 43px, grid icon. The exit to the full ledger.
  2. שיתוף כשל מס׳ 13 — gold fill, 46px, repost icon — the arrow loop upright, TikTok-style: two interleaved L arrows, up the left column and down the right, drawn 16 × 15 — a compact near-square loop, not a tall narrow one, naming the item rather than saying "share the failure". The only gold-filled action outside slide 5's save.

Two versions, and the choice is not the design's

Slide 6 exists in two fully specified forms. This document does not decide which one ships — it specifies both and hands the choice over. Everything above this heading is common to the two; everything below differs.

10 · What the data must provide

This is the shape the six slides call for. It is written as a diff against the schema as it stands, because that is the clearest way to read it — but the direction runs from the screens outward: these fields exist because a screen needs them, and a screen that needs one is not redrawn because the field is missing. Anything here that cannot be met is a shortfall to record in §12, not an amendment to §1–§9.

// data/schema/index.ts

- Summary = { stage, lines: [{ text, cites: string[] }] }
+ Summary = { stage, text }                 // markdown; cites are [label](i13-c08) links

  Incident = {
    id, parent, he,
-   summary,                                 // narrative, item-specific
+   summary,                                 // markdown, SYSTEMIC — no 7.10 manifestation
+   card_line?,                              // short statement for the slide 6 card
+   opinion?: { question, failed, since, caveat },  // slide 5's head — generic in substance,
+                                            //   phrased in THIS item's context
+   photo?: {
+     portrait?:  { file, photographer, source, licence, place, year },   // the gate
+     landscape?: { file, photographer, source, licence, place, year },   // slide 6 card
+   },
+   feedback_strip?,                         // override on the global star-strip flag
    illustrative, claims, summaries?
  }
  • A systemic description per incident (slide 2) and an overview per reached stage (slide 3), in markdown: paragraphs, bullets, inline bold on key phrases. Presentation interprets the markdown; there is no separate "bottom line" field.
  • Cite chips are markdown links whose target is a claim id. The sources carousel is pure presentation — the unique claims the text links to.
  • Validation parses the markdown: every sentence is cited, every link resolves to a claim of that incident, and inline bold mid-sentence is accepted.
  • The unreached-stage statement is computed, not authored — a fallback, not a field. So is the stage date, the item number and the gate's source line (§4).
  • A reached stage with no overview is not an error — it renders its claims (§6).
  • Two photo crops per incident, portrait and landscape, each optional and each with its own credit. Dimensions are not validated; the crop is trusted. Sourcing and licensing are DIA-366.
  • Deep links per slide and per stage (§2).
  • The slide 5 question, authored per incident — generic in substance, phrased in that item’s context. A stage-level default may back it up; it does not replace it.
  • Analyst commentary records and public answers — specified in §8, built after the MVP.
  • Somewhere to put a star rating, if version B of slide 6 is the one that ships (§9).
